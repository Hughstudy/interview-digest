## 分章详解

### 第一章：开场——数据公司估值狂飙（00:00-04:50）
（开头 1 分钟为 Alignment 2026 黑客松广告，一句带过。）Yiwen 用三个锚点数字解释"为什么现在要聊数据"：AfterQuery 由三名 20 多岁的年轻人创办，今年 4 月 A 轮估值 3 亿美元，到 9 月新一轮融资被推到 32 亿美元——不到半年 10 倍，创下 YC 旗下公司从启动到独角兽的最快纪录；Meta 去年入股 Scale AI 时给出超 290 亿美元估值；Mercor 去年 10 月融资估值也到 100 亿美元。她随即点出全片核心疑问：这些高估值背后的数据生意，外界其实看不清——数据公司究竟在卖什么？模型公司为什么愿意付这么多钱？她提前勾勒出三层递进的答案：现在的数据公司早已不只是"给图片打标签"的人工标注，而是要请行业专家把"一个回答/一份工作成果满足什么条件才算好"写成评分细则（Rubric），再进一步搭出让 AI 实际动手的强化学习环境（RL environment）——配上任务、工具和反馈机制，让模型在里面反复操作、按结果学习。这一章给整期节目定下"出题—卖题—判卷"的拆解框架，后面每一章都在回答其中一环怎么运转、钱怎么流动。

### 第二章：生态图谱——五种基因的数据公司（04:50-08:20）
允中按"出身"给行业画地图，这是理解竞争格局的关键：第一类是招聘基因，如 Mercor、Handshake——Mercor 有自动 AI 面试产品，核心能力是"短时间内找到足够量的专家"，靠专家网络扩张；第二类是 Scale AI 这样的传统数商，从众包网络起家；第三类做合成数据；第四类是领域公司转行——他特别提到具身智能行业的一个扭曲现象：很多做模型的公司暂时没赚到钱，但花了大量精力投资采集素材，就"顺便做起了素材生意"；第五类是数据经纪人（broker），比如好莱坞有人手握大量版权数据、知道怎么卖出去。头部玩家（Mercor、Surge AI、Scale）试图什么都 cover，新秀则在垂直领域做深（如偏研究工程、主产代码和 tool call 数据的 BigCode、Snorkel AI）。允中还点出每个数商都面临的取舍：全职自养标注员质量高但产能死板，众包网络灵活但个人质量难保障——Scale 的优势恰恰是"不光在数据上、也在人上"的质检经验。这章建立了后面所有商业讨论的演员表。

### 第三章：需求三次跃迁——从人工标注到 RL 环境（08:20-12:10）
这章是全片技术含量最高的概念梳理。允中先讲自己的入职时机：他在 Meta 入股 Scale 之前签的 offer，"一到人就走了"，亲历整个行业人才战争和薪酬体系"Go crazy"的过程。需求侧的转折点在 2024 年：之前数据=海量众包标注喂预训练；Deep Search 兴起后行业转向 Agentic data。他解释了这条演化链的内在逻辑：预训练"干得有点无聊了"（继续 scale 调数据配比），o 系列模型证明 RL 跑通后，大家兴趣全在 RL 上——而 RL 需要可验证的信号。数学最容易（选择题对错、数字核对），但推广到医疗、金融、指令遵循时遇到问题：这些领域有标答，但标答不结构化。他给了一个精准比喻："就好像我去答历史考题——历史考题是有标答的，但每个人的写法都不一样，很难做模式匹配。"解决方案就是 Rubric："相当于我让一个 TA（助教）拿着教授写的打分规则来给你打分。因为这个打分规则是提前标好的，是教授写的，所以这个 TA 也不需要特别聪明。"这就是大模型数据的核心概念 weak-to-strong supervision——用弱模型监督强模型，成立条件是专家先把脑海里的知识写下来。再往前一步，模型要"动手"了：不只是验证聊天输出，而是在 Agent 环境下配工具、配沙盒、检查"数据库是不是真的写入了"，验证方式变成程序化检查 + rubric + 偏好打分的混合，且各家流派不一（Terminal-Bench 就纯程序化、不要 rubric）。

### 第四章：分歧——Rubric 到头了吗？（12:10-15:30）
这是全片第一场真正的观点交锋。允中说"Rubric 感觉已经过时了，大家都在讲 RL environment"，依据是行业趋势：容易收集的专家 rubric 已经"收集得比较干净了"，Mercor、Surge AI 的崛起正与这波专家 rubric 红利相关。一铀直接反驳："我跟允中的看法有一点反过来了"——他认为专家主观判断题这类 rubric"其实还做得远远不够"。他讲的依据是 ALE 的初衷：vibe coding 之所以发展那么快，是因为 coding 领域 benchmark 密集且容易验证（确定性 rubric），大家为了刷榜在这上面疯狂投入；用同样思路，如果在工程等其他领域能建立"客观打分"的评测体系，"只要你刷的是有益的分、有意义的题，模型带来的提升对于人的日常工作来说就是实打实的提升"。允中随后收窄了自己的立场：他说的"到头"指的是行业趋势从静态文本问答转向要动手的 knowledge work，"纯文本 rubric 需求量小了一点，但还是很大"。一铀补充了工程产出的验证难题：除非把输入固定得特别死，输出可能性极多（连数学解法都不唯一），确定性对比 ground truth 会造成误判。他还抛出一个具体设想：游戏"好不好玩"其实有科学指标——游戏设计教科书里有"奖励曲线是否平滑、是否符合大脑多巴胺机制"的评判方式，但目前没有一个公开 benchmark 做完整了这件事，因为需要专家更深度参与。

### 第五章：Rubric 与验证器共同进化（15:30-20:00）
允中用一句话概括整个验证体系的演进思路："大家希望左脚踩右脚"——模型变强→验证器变强→可以允许更复杂的 rubric→知识可以从 rubric 转移给验证器。弱验证器时代只能写"傻子都能看出对错"的规则；模型能力上来后 rubric 可以写得越来越模糊。但他强调一条硬约束："rubric 加上验证这两块加起来的知识和能力，应该比我要训练的模型要多，不然就达不到训练模型的目的了。"具体案例是生图：指令遵循部分（图里有猫有狗、背景板写了哪几个字）可以写成 rubric，甚至跑 OCR 提字核对；但"这个猫要是一只可爱的猫"这种主观维度，可能要专门训练一个掌握了人类主观体验的 reward model，与 rubric 混合使用。一铀则从人机分工角度补充：历史脉络是 Cursor 时代人类参与执行代码→Agent 能力变强后"人负责决策、Agent 负责执行"；决策说得越清楚，输出越固定，rubric 就越确定；反之，如果未来 Agent 连决策也接管——比如上市公司高层的决策——"你该如何去 train 一个 reward？它每天的任务都在变，你很难收集到足够的数据"。这为后面 ALE 的众包思路（把人的历史决策收上来）埋下伏笔。

### 第六章：卖题与判卷的利益链（20:00-23:40）
这章拆解行业的商业本质。允中的分析：评测体现的是"模型距离理想状态的 gap"，本质是科学研究；但提升模型能力的数据与榜单评测方式息息相关——这就产生了微妙的生意：构造 benchmark 的人对该领域认识深，"自然就有了卖数据的权威性，大家会比较相信你手上卖的数据，这个生意就这么产生了"。他甚至当场问一铀：ALE 做火了，应该不少人问你卖不卖数据、VC 想不想投吧？一铀立刻敲警钟：他私下听说有数据公司踩了红线——把正在做评测的数据拿去卖。"这是大家千万不能碰的一条线：不能让你做的生意污染 benchmark 的权威性，不然你不仅毁了你的 benchmark，也毁了其他人的模型。"他给出的分工定义很清晰："benchmark 面向的是未来，做数据面向的是现在。"ALE 今年 1-2 月做的时候，模型平均分只有 10%-20%、大部分题目零分，他曾担心评测太难失去意义，后来想通了：benchmark 本来就是做给未来的模型的。对 bench-maxxing（刷榜）他也给了反直觉辩护：只要 benchmark 跟真实用户体验非常接近，"bench-maxxing 不一定是一个贬义词"。这章是理解"为什么出题人不能卖题"的关键——评测的公信力是整个数据市场定价的地基。

### 第七章：什么是好评测（23:40-29:00）
允中给模型公司视角的优先级：做能力提升"最大的 ROI 还是放在能力上"——如果一次改进只涨这一个榜、别的都不涨，那可能有问题；好信号是泛化性，一项核心认知能力的提升应该惠及多个 benchmark。他总结两类好评测：一是反映核心认知能力，二是贴近用户在意场景（如 personal assistant/Muse），后者"甚至未必测的是模型本身，可能测的是你的 harness"——分数低可能是工程问题而非模型问题。一铀补充两个行业洞察：第一，Artificial Analysis 这类聚合榜单给各家 benchmark 配权重，但"这个权重是不是大伙需要的权重"很主观，大家质疑的更多是榜单本身而非模型，所以 Anthropic、OpenAI 都倾向自建评测体系贴近自己心目中的分布，第三方验证只用来对外发布时增强说服力；第二，榜单走红有随机性——Scale 做了 SWE-Atlas 的三种风味（代码仓库问答 Q&A、代码重构、写测试），分三阶段推出，结果最简单的 Q&A 先被 AA（Artificial Analysis）捡去上了榜，大家突然都来刷，"我们当时很不理解：花了那么多心血做了更复杂的 benchmark，结果就因为时间关系"——你在 tech report 上看到什么上榜，背后有相当随机性。他还提到 ARC 这类测 agent 智力的小游戏 benchmark 的悖论：初衷是解游戏代表人类智力，结果"这个智力也可以做得特别特化，一个小模型也能把它搞出来"。

### 第八章：真实分布 = 用户体验（29:00-33:30）
一铀把"理想分布"拉回第一性：真实分布本质上就是大家的用户体验——类似 LMArena 模式，每天给 agent 一个 prompt、多个模型同时执行、实时打分，这是最真实的评价。但 LMArena 之前能做好是因为 QA 快、开销低、几秒出答案可以马上打分；Agent 时代一个长程任务动辄几个小时，用户没有超能力每次开几个 agent 一起跑，也没有机制收集反馈，所以真实 ground truth 拿不到。允中从 Meta 搜索推荐的老本行接话：产品成熟、用户体量够了之后，最终关心的还是用户增长，"最后就朝着赚钱的方向走"——看哪些指标跟 DAU 增长最相关。但大模型与搜推不同：场景太复杂，总有新东西出来（现在大家卷科学发现，"我不可能有足够量的科学家给我显著的 A/B test 结果"），所以必须依靠构造 benchmark。他给了个具体观察：很多评测 benchmark 跟线上 A/B test 测出来结果不一样，用户也主观——聊天产品喂 factual 内容和喂 clickbait 说好听话，反馈可能相反。一铀的案例是 Claude Code vs Codex：Claude Code 在 LMArena 上分数遥遥领先，因为他输出格式更贴近人们想看到的样子；Codex 执行更细致但输出不好懂，"稍微吃了点亏"——但他个人体验两者不相上下，甚至更偏好 OpenAI 一点，"因为它做得更细致、犯的错误更少"。非头部 lab 则高度依赖外部评测，因为内部评测团队没经验，人力更愿意投在训练上。

### 第九章：采购——新的行业卡点（33:30-38:50）
这章解释小团队的创业窗口和真正的壁垒。最近兴起的 RL environment 公司其实更多在做合成：交付一整套环境需要大量工程工作，合成技术栈强的小团队（四五人甚至两三人）能在短时间交付大量合成环境，因此拿到高估值。但这波机会的成立有前提——今年大家卷代码，而"软件行业是最奇怪的：非常 open、大量公开资料、生产数据的公司自己也懂代码"。往垂直领域走就复杂了：允中把后训练数据拆成"采购 + 加工"两环——采购原材料（ALE 的众包上传就是新激励机制），加工成训练环境。采购正变成卡点：代码领域要采私域代码仓库；芯片设计要把整个设计环境造出来、解决商业软件版权；DevOps 领域有公司做了整套 AWS 模拟器。一铀给出的标价案例很震撼：ALE V2 想收一个 Steam 游戏库做游戏开发任务，一个名不见经传、几千用户量的 MOBA 游戏，源码要价"两三百万人民币一条"——"哪家数据公司都没有这个财力"。医疗是另一个热门但数据极少的垂类（病例数据敏感）。他还做了个统计：把 Nature 出版物的生物学子学科分类树展开到第三级约 3000 个节点，现有 life/bio benchmark 覆盖不到 5%-10%，"连一个覆盖面完全成型的 benchmark 市面上都没有，更别说针对它做数据"。

### 第十章：数商的本质是研发（38:50-44:10)
回答"这波合成数据公司能赚多久"。允中的判断框架分两层：第一性原理上"还有巨量的问题没解决，世界上还有多少东西没被蒸馏干净是巨大的机会"；但看现状，竞争者越来越多、margin 越来越低，"只盯着手上的工作一定越来越难做"。一铀举证数据贬值速度：以前影印奥数课本就能批量造数据，"这些数据现在基本上是零价值"。允中的结论是"一个好的数商最后解决的是研发问题"——像软件公司一样提前投入未来需要的东西，赚到钱再投下一个。他甚至提出"暴论"：lab 未必有最好的基因解决数据问题。理由之一是 deadline 都很死，lab researcher 没有花半年深挖一个行业的自由度，这时有数商说"我把那个行业搞清楚了，你要不要"，大家通常都会看一眼；理由之二是利益冲突——lab 一边把 FDE（前线部署工程师）派进企业，一边自己搞企业数据，"如果我是一个企业，我是不太放心把我的数据交给你的"，所以第三方采购有长期存在的结构性理由。头部 lab 的反向动机也存在：不希望所有人都能从数商获得同样能力（希望第一方独占），所以也在做 expert matching（把人直接派进 lab）。

### 第十一章：数据怎么用——训练配方与防作弊（44:10-48:20）
这章讲交付细节。数据按类型对应固定训练方式（training recipe）：简单数据直接 SFT（把对的答案喂进去）；rubric 类做强化学习（模型不停被打分）；RL 环境类做长程任务。今年主题是 RSI（recursive self improvement，递归自我改进）——允中坦言"其实是个 buzzword"，指 AI 自己研发自己：跑一把要几天到一星期，中间要有 GPU 真的在那儿"模型训模型"，训练方式开始变得模糊、还没有共识。防作弊（reward hacking）是造环境最怕的：任务没完成但"使了手脚"分却很高，训出来的就是耍滑头模型。现有技术是用 agent 做 red team，再让强模型专门试着找捷径。允中还透露 reward 的多维设计：不只看任务完没完成，还看消耗了多少 token、多少步数——"各种各样维度的检查、reward、防止作弊，结合起来才能完成一个训练的 recipe"。定制服务包括难度适配（模型厂商把未发布模型给 Scale，帮它筛"不能太难也不能太简单"的题——RL 是让模型自己试，试对了才能学到东西，太难就啥也学不到）和轨迹采集（把客户模型的轨迹采出来筛选，甚至用人解出可复现的轨迹让客户直接拿回去做 SFT，跳过 RL）。

### 第十二章：污染与造假（48:20-53:00）
从 OpenAI 2026 年 2 月停止报告 SWE-bench Verified 分数讲起：OpenAI 指出两类问题——测试本身有缺陷（功能正确的解法被判错）和数据污染（特定提示下模型能复现题目原本的人类修复代码，说明训练时见过）。一铀补数据：SWE-bench Verified 过去 6 个月只从 74% 提升到 80%，剩下的 20% 集中在脚本太严苛、题目本身不可解等问题上，"这个 benchmark 本身可能就失去了对比的意义"，所以 ALE 连 Verified 版也不采用。更麻烦的是专家造假：ALE 的奖励机制是提交被接受就进作者列表，确实有人"为了提交而提交"，起 agent 合成一堆乱数据，"有些数据交上来我肉眼看出来就是编的"，甚至有人把法院证据这类敏感材料交上来（已筛掉）。允中呼应：Scale 用小时工也遇到偷懒作弊，"奖励机制是个特别特别难的问题"，他的设想是 proof of work——要求把整段工作流程录下来、必须达到时长，让造假的成本高于收益。污染检测的难度分层也清楚：公开数据污染最好查（直接问 agent 都能找到）；最难的是编造数据——比如根本没跑过的化学模拟、自己编一套似是而非的结果，"没有几个月根本查不出来，因为它看上去很真"，通常要等所有 agent 能力远超问题本身、发现大家答案一致但与真实答案不符时才暴露，而让另一个专家验证的成本极高（这题本身要专家做一两个礼拜，验证的专家自己也可能偷奸耍滑）。一铀总结："众包的 benchmark 为什么难做？就是难做在这里，人性是非常复杂的。"本章末尾还有个重要观点：95% 以上的真实工作流任务都能划归为 coding 问题（3D 建模走 FreeCAD API、MCP 调用），因为"代码就是 agent 的手跟脚"。

### 第十三章：终局——PE 新玩法与估值天花板（53:00-58:00)
