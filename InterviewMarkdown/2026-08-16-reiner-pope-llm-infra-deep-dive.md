## 0. 先用 60 秒回答你的两个问题

**Q1: 大模型是怎么 train 的？**
三个阶段烧三种算力：①**预训练**（pre-training）——把整个互联网的文本喂给模型，做"下一个词预测"，公式是 6ND（6 × 参数量 × token 数），这是大头；②**强化学习**（RL）——让模型生成大量解题过程（rollout），挑好的回炉训练，因为要"生成完整答案再训练"，每 token 有效成本是预训练的 2~6 倍；③留给**推理**（inference，就是上线给用户用）的算力。Reiner 用"三项成本大致相等"的启发式推出：**前沿实验室大致把算力 1/3 预训练、1/3 RL、1/3 推理**，且每个模型的**推理总 token 量 ≈ 预训练总 token 量**（约 150~200 万亿）。这解释了为什么现在的模型普遍"过度训练"到 Chinchilla 最优的 ~100 倍——多花训练算力买一个更小、推理更便宜的模型，就像多花钱开模，把单件制造成本打下来。

**Q2: 怎么决定怎么 serve（上线服务）？**
全部决策从两条 roofline 公式出发：**一个 token 的延迟 ≥ max(算力时间, 显存读取时间)**。算力时间 = 激活参数量 ÷ 芯片算力；显存时间 = (总参数 + 批内所有用户的 KV cache) ÷ 显存带宽。由这两条公式能推出整个行业的行为：最优 batch size ≈ 300 × 稀疏度（几千路请求拼车）；每 ~15-20ms 发一班"火车"；MoE 专家摆在单个机架内（expert parallelism），很少跨机架流水线（pipeline parallelism）；上下文长度卡在 200K 是因为显存带宽墙；API 定价的每个数字（长上下文 +50%、输出 5 倍价、缓存命中 10 倍便宜）都是这两条公式的直接泄漏。

一句话总结全片：**看懂了 batch size 和两条 roofline 公式，API 定价表、模型架构选择、AI 进展速度就都"说得通"了。**

## 1. 名词表（按出场顺序，遇到不懂随时翻回来）

| 术语                                | 通俗解释                                                                                                                | 类比                              |
|-----------------------------------|---------------------------------------------------------------------------------------------------------------------|---------------------------------|
| **token**                         | 模型读写的最小文字单位，约 0.75 个英文单词                                                                                            | 文字的"乐高积木块"                      |
| **参数 / weights（权重）**              | 模型学到的数字，存放在显存里。DeepSeek V3 共 671B 总参数，每个 token 只"激活" 37B                                                            | 员工总人数 vs 每单实际经手的人数              |
| **前向传播 forward pass**             | 输入一段 token，经过所有权重矩阵相乘，算出下一个 token                                                                                   | 流水线走一遍                          |
| **反向传播 backward pass**            | 训练时从损失出发反向算每个参数的梯度（算力是前向的 2 倍，所以训练=2+4=6）                                                                           | 流水线倒着走一遍找问题                     |
| **decode（解码）**                    | 一个 token 一个 token 逐个生成。每生成 1 个新 token 都要跑一遍完整前向传播                                                                   | 逐字写信，每写一个字都要重读全部前文              |
| **prefill（预填充）**                  | 把用户输入的长文本一次性并行处理（读文件、读代码、用户的长提问）                                                                                    | 粗读：一目十行                         |
| **KV cache**                      | 模型对已读过的每个 token 存下的"读书笔记"（K=内容键，V=内容值）。生成新 token 时要翻看**所有**历史笔记。每个用户独有、不能共享                                         | 你读一本书时在页边写的批注，写信时每写一个字都要翻一遍所有批注 |
| **Q heads / KV heads**            | 注意力头分两种：**Q 头**是"检索头"，只被正在生成的那个 token 临时用一下；**KV 头**是"存储头"，负责把历史 token 的内容存进显存。存多少 KV 头直接决定每 token 的笔记字节数（通常 1~8 个） | 检索用的索引卡片 vs 存档的书架               |
| **batch / batch size（批）**         | 同时拼在一辆车里服务的请求数。权重只需读一次，全批共享                                                                                         | 拼车：固定成本（司机+油费）摊到 N 个乘客          |
| **FLOPs**                         | 每秒浮点运算次数，芯片的算力指标                                                                                                    | 发动机马力                           |
| **显存带宽 (memory bandwidth)**       | 每秒能从显存搬多少字节到计算单元。B200 单卡 8 TB/s                                                                                     | 装卸口的吞吐能力                        |
| **显存容量 (memory capacity)**        | 显存能装多少字节。决定权重+KV 放不放得下                                                                                              | 仓库面积                            |
| **HBM**                           | 高带宽显存（High Bandwidth Memory），AI 芯片专用。注意：推理时 HBM 访问**几乎全是读**——权重只读，KV 也以读为主                                          | 仓库 vs 装卸口：面积再大，装卸口窄也白搭          |
| **roofline 分析**                   | 只看"算力上限"和"带宽上限"两条线，取较慢的那个当瓶颈                                                                                        | 木桶原理：算力短板 vs 带宽短板               |
| **MoE（混合专家）**                     | 模型里有几百个"专家"子网络，路由器每个 token 只送往少数几个专家。总参数大、激活参数小                                                                     | 大医院：分诊台把每个病人只送到 2-8 个科室，不用全院会诊  |
| **稀疏度 (sparsity)**                | 总参数 ÷ 激活参数。DeepSeek V3 ≈ 671/37 ≈ 18                                                                                | 挂号费便宜因为不用全院出动                   |
| **dense / sparse attention（注意力）** | dense：每个新 token 看完所有历史笔记（成本线性涨）；sparse：只挑一部分看（DeepSeek 发表的机制能把线性项降到约 √L）                                            | 通读全书 vs 只看目录+重点章节               |
| **机架 (rack)**                     | 数据中心里一个几米高的柜子，装 ~64 块 GPU，受电力/重量/散热/线缆密度物理限制                                                                        | 一栋楼里的一个楼层                       |
| **scale-up 域**                    | 机架内部网络（Nvidia 叫 NVLink），任意两卡两跳直达                                                                                    | 楼内电梯                            |
| **scale-out 网络**                  | 机架之间的网络，带宽约为 scale-up 的 1/8                                                                                         | 跨园区货车                           |
| **专家并行 (EP)**                     | 不同专家放不同 GPU。机架内任意卡互传（all-to-all）                                                                                    | 每个科室占一间诊室                       |
| **流水线并行 (PP)**                    | 模型的**层**切到不同机架，token 像流水线一样流过                                                                                       | 工厂工序：车间1→车间2→车间3                |
| **张量并行 (TP)**                     | 把单个矩阵切开放多卡。现在专家本身够小，已不值得用                                                                                           | 把一张大桌子锯成两半分给两个木匠                |
| **数据并行 (DP)**                     | 同一份模型复制多份，各喂不同数据                                                                                                    | 同一菜单开多家分店                       |
| **micro-batch（微批）**               | 为填满流水线把大批切成小块轮流喂                                                                                                    | 一条传送带上同时有几批货                    |
| **气泡 (bubble)**                   | 流水线中某工位等料的空闲时间                                                                                                      | 工人等上道工序                         |
| **Chinchilla 定律**                 | 2022 年 DeepMind 的结论：给定训练算力，最优配比是每 1 个参数喂 ~20 个 token                                                                | 教科书和学生的最优配比                     |
| **over-training（过度训练）**           | 用比 Chinchilla 最优更多的数据训练一个更小的模型。训练时多花钱，推理时每个 token 更便宜                                                               | 多花钱开模，单件制造成本更低                  |
| **6ND 公式**                        | 训练总算力 ≈ 6 × 参数量 × token 数（前向 2 + 反向 4）；纯推理只要 2ND                                                                    | —                               |
| **MFU**                           | Model FLOPs Utilization，实际用上的算力占比。decode 通常比训练低                                                                     | 产能利用率                           |
| **drain time**                    | 显存容量 ÷ 显存带宽 = 把整块显存读一遍的时间。HBM≈20ms，DDR≈秒级，Flash≈分钟级，机械硬盘≈1小时                                                        | 把整个仓库的货搬空一遍的时间                  |
| **rematerialization（重算/复活）**      | 不存笔记，要用时从原始 token 重算一遍                                                                                              | 不留底稿，要看就重新推导                    |
| **all-to-all 通信**                 | 每张卡都要跟其他所有卡说话                                                                                                       | 全公司两两互寄包裹                       |
| **rollout**                       | RL 里模型生成的一整条解题过程样本                                                                                                  | 学生交的一份完整答卷                      |
| **投机解码 (speculative decoding)**   | 小模型先一口气草拟 N 个 token，大模型一次前向并行验证——Fast Mode 提速的另一块拼图（⚠️ 视频开头提到"待会儿回来讲"但全片没有回来，此处为整理者补充背景）                            | 实习生打草稿，老板批量签字                   |

## 2. 章节深度解读（15 章 + 2 附录）

### 第 1 章（00:00–01:40）开场谜题：为什么加钱能变快？

**本章问题**：Claude/Codex/Cursor 的 Fast Mode——付 6 倍价格，流式速度快 2.5 倍——机械上发生了什么？能否付 100 倍价格换 10 倍速度？反过来，能否出个"Slow Mode"，愿意等几分钟就打折？

**讲透**：Reiner 先给结论：**主导效应是 batch size（拼车人数）**，第二个效应是投机解码（小模型先猜几个词、大模型批量验算），后面整堂课就是把"batch size 如何同时决定延迟和成本"量化出来。这个开场问题的完整答案在第 3、4 章，先把谜题记下：**延迟有下限（权重要从显存读一遍，物理上省不掉），成本也有下限（每个 token 的算术量省不掉）**——所以 100 倍价格买不到 10 倍速度，"Slow Mode" 也便宜不了多少（你已经在成本的底板上了）。

**背景花絮**：这是 Dwarkesh 为"黑板课"新格式专门建的首期节目。开场他主动披露：**本人是 MatX 的天使投资人**（但声明与本期内容无关）——听的时候记得这层利益背景。

**连接主线**：这一章立了整堂课的靶子——用黑板推导解释一个商业现象。

### 第 2 章（01:40–16:00）两把尺子：算力时间与显存时间（全片地基）

**本章问题**：怎么估算"生成一个 token 要多久"？

**讲透**：Reiner 的方法论是**下界估计**：真实时间算不准，但一定 ≥ 两条下限中较慢的那条（roofline 分析）：

- **算力时间** t_compute = **激活参数量 × batch size ÷ 芯片 FLOPs**。矩阵乘法的总运算量除以马力。DeepSeek V3 每个激活 token 约 37B 参数。（注意力计算的 FLOPs 其实很小，先忽略——为什么可以忽略见第 14 章的二次项讨论。）
- **显存时间** t_memory = **总参数 ÷ 显存带宽 + batch × 上下文长度 × 每token字节数 ÷ 显存带宽**。第一项是**读权重**（671B 参数全要读，不管激活多少——这就是总参数和激活参数的区别！），第二项是**读 KV cache**（每个用户读自己那份完整"读书笔记"）。

这里 Dwarkesh 插问了全片最重要的名词解释——**KV cache 是什么**：decode 时每生成一个新 token，这个新 token 要"看"它前面**所有**历史 token，但它看的不是原始文字，而是模型对每个历史 token 算出的内部表征（K 和 V 两个向量），这些表征缓存下来就是 KV cache。**注意力这个动作本身主要是搬数据，不是算数**——所以它在显存时间那边记账。一个支撑细节：推理时 HBM 的访问**几乎全是读**——权重矩阵只读不写，KV cache 也以读为主，这个事实是后面 drain time（把显存读一遍的时间）分析成立的前提。

**关键不对称**：权重是全批共享的（读一次服务 2000 个用户），KV cache 是每用户独有的（2000 个用户 = 2000 份笔记）。这个不对称是后面几乎所有结论的根源。

**连接主线**：后面所有曲线、定价、架构决策都是这两条公式的变形。

### 第 3 章（16:00–27:00）batch 的经济学：千倍成本差与最优批大小

**本章问题**：batch 到底多重要？多大算够？

**讲透**：先画**延迟 vs batch** 曲线：算力时间随 batch 线性上升（斜率固定）；显存时间里权重读取是不随 batch 变的常数，KV 读取随 batch 线性上升。总延迟 = max(两条线)。batch 小时是显存墙（权重读取主导，延迟平），batch 大时是算力墙（线性上升）。**两条线斜率相等的那个点，就是你"恰好同时打满算力和带宽"的甜点**——Reiner 原话："Whenever we have balance points, it says that you're getting it exactly right"（出现平衡点，说明你恰好做对了）。

Dwarkesh 在这里追问了一个很实际的问题——**"假设甜点在 100K 上下文，你跑到 200K，MFU 会掉到 50% 吗？偏离甜点区代价有多大？"** Reiner：**按此模型，是的**——memory 时间随上下文线性涨、compute 不变，跨过拐点后多出来的部分全是浪费带宽。这就是为什么服务商都要守在"Goldilocks 区"（不冷不热刚好），也是后面第 13 章 Gemini 200K 定价拐点的理论来源。另一个细节：这个"线性"只对 dense attention 成立——**DeepSeek 发表的稀疏注意力机制能把这项开根号**（√L），但各家实验室实际用多稀疏，外界很难知道。

再画**单 token 成本 vs batch**（延迟 ÷ batch）：权重读取一项除以 batch 后变成一条下滑曲线——batch=1 时成本趋近无穷（独享整个模型读一遍的开销），batch 越大权重开销摊得越薄，最终成本逼近"纯算力"这条水平地板。**不拼车 vs 拼车 2000 路，成本差可以到 1000 倍**——这就是为什么所有推理服务商必然做大 batch。这也直接回答了开篇"Slow Mode"之问：慢模式只能躺在成本地板上，没有下探空间——权重读取已经被大 batch 摊没了，KV 和算力是每个用户实打实的增量，等再久也省不掉。

**最优 batch 的闭式解**：令权重读取时间 = 权重乘法时间，即 N_total/BW = B × N_active/FLOPs，解出

*B = (FLOPs ÷ 显存带宽) × (总参数 ÷ 激活参数) ≈ 300 × 稀疏度**

FLOPs/带宽这个硬件比值（按 FP4 半字节折成无量纲）在 A100→H100→B100 三代都稳定在 **~300** 上下——算力和带宽一直在同步涨，这个比值没变过（Dwarkesh 专门问了"这个比值随硬件代际变过吗"，答案：没有，FLOPs 和带宽同步增长），所以最优 batch **只由模型稀疏度决定，和模型多大无关**（反直觉结论，Dwarkesh 也愣了一下："这完全取决于稀疏度，不取决于模型规模，这结果很有意思"）。求出 B* 后实践上还要再乘 2~3——因为真实世界的效率不如 roofline 理想，人们不想正好卡在平衡点上。

> ⚠️ **事实核查注**（视频 vs 官方口径）：Reiner 口述"DeepSeek 激活 32/256 个专家，稀疏度=8，B*≈2400"。DeepSeek V3 官方配置是每 token 激活 **8/256** 个路由专家（+1 共享专家），整模型稀疏度 671/37≈18。按整模型口径 B* = 300×18 ≈ **5400**；按他口径 2400 再"加倍到三倍"也是 5000-7000。两个口径殊途同归：**最优 batch 在几千这个量级**，公式方法本身完全成立。

**连接主线**：几千路拼车 → 那"凑满一车"要等多久？下一章。

### 第 4 章（22:30–27:00）20 毫秒一班的火车：排队延迟从哪来

**本章问题**：batch 2000 是不是要等 2000 个用户同时来？等待多久？

**讲透**：运营方式是**定时发车**：选定一个 batch size，比如每 20ms 发一班"火车"，到点就走——满了拉满的，没满也走（"train departure model"，Dwarkesh 的比喻，Reiner 全程沿用）。新请求最坏情况：刚错过上一班（等 20ms）+ 下一班开完（20ms）= **最坏 40ms 额外排队延迟**。这就是拼车的代价，而 40ms 用户根本感知不到。

**20ms 这个数怎么来的**（Dwarkesh 追问"这只是经验法则吧，它从哪来的还没讲"）：来自**显存的 drain time = 容量 ÷ 带宽**。前向传播一遍要把（几乎）整块显存读一遍：权重读一遍 + 所有用户的 KV 读一遍 ≈ 把显存搬空。Rubin 代际机架：288 GB ÷ 20 TB/s ≈ **14.4ms**（我复算 ✓，视频说 ~15ms）；多代 HBM 都落在 15-20ms 附近——这不是巧合，是硬件设计者刻意让容量和带宽匹配，使得"整块显存读一遍"恰好是一次前向传播的节奏。为什么不把发车间隔设成 30ms？因为那样显存要读两遍，纯属浪费（权重和笔记读一遍就够了）。

**连接主线**：几十 ms 一班 × 每班几千 token = 一台机架的吞吐——下一章算这台"印钞机"的产能。

### 第 5 章（27:00–31:00）一台机架值多少流量：128K tokens/s、Gemini 的千分之一、中心化之问

**本章问题**：batch 2000 用户算多吗？小服务商能达到吗？batching 的规模经济会不会把行业推向赢家通吃？

**讲透**：把 batch 换算成吞吐：每 15.6ms（1/64 秒）发一班 × 每班 ~2000 token = **每台 Blackwell 机架 ~128,000 token/s**（2000×64=128K，我复算 ✓）。

对照全局：Gemini 去年公告吹的全球流量是**数亿 token/s** 量级。一台机架 = Gemini 的**千分之一**。含义有三层：①要在 AI API 市场竞争，你至少得能服务 Gemini 流量的 1/1000，一台顶级机架刚好够——**这就是入场券价格**；②对巨头来说，batch 几千路轻轻松松就凑满（全球用户请求像下雨一样），所以"凑批等待"根本不是问题，上一章的 40ms 排队是全部代价；③**Dwarkesh 的中心化之问得到了否定答案**——他问"batching 的规模经济是不是强烈推向中心化？"，算完发现 2000 并发用户根本不是门槛（"2000 个同时在线用户很多吗？看起来不多"），**推理规模经济的中心化推力比想象中弱得多**：一台机架就能达到有竞争力的吞吐，小玩家买一台机架即可入场，不需要万亿级集群。（对比：预训练侧确实有强中心化推力——那才是巨头护城河。）

**连接主线**：batch 能凑满 → 稀疏模型的算力优势就能吃满 → 下一章讲为什么大家都冲向稀疏（MoE）。

### 第 6 章（31:00–37:30）MoE 的汇率：64 倍参数换 4 倍等效

**本章问题**：稀疏度越高（激活参数越少），算力越省，但模型质量掉多少？这笔交换划算吗？

**讲透**：这是纯经验问题，没法从公式推——Reiner 明确说"不幸，这无法解析地回答，是经验性的模型质量问题"，然后拿出**他自己参与的论文**《Unified Scaling Laws for Routed Language Models》（Google，2022）：固定激活参数 370M，把专家数从少加到 64，质量一路上升；64 专家 × 370M 激活 ≈ 23.7B 总参数的 MoE，效果 ≈ **1.3B 的 dense 模型**。换句话说：**用 ~18-64 倍的总参数，买到 ~3.5 倍的等效 dense 能力**（视频里两人当场对数："64 倍换 4 倍？"）。汇率看起来很烂？算总账是纯赚：

从第 3 章公式看：激活参数 ÷ 算力 = 算力时间变小（每个 token 便宜）；总参数变大只增加权重读取，而权重读取被 batch 摊薄——**batch 越大，总参数的显存开销越接近免费**（"从我们这套分析的观点看，这是纯赢——一直加，直到用户不够凑批为止"）。Dwarkesh 把这条逻辑链完整复述了一遍：想少算→更稀疏→需要更大 batch→需要更多显存容量装 KV→于是又回到硬件。限制只有两个：①显存容量要装得下更大的总参数（第 11 章）；②专家越多路由通信越多（第 7 章）。另外 MoE 技术本身迭代很快——2017 年就有，GShard/Switch Transformer 是老一代，DeepSeek 的"激活更多但更细的专家"是大创新，老论文的汇率数字未必适用于新一代。

**连接主线**：MoE 是主流 → 那几百个专家物理上怎么摆？下一章进机架。

### 第 7 章（37:30–46:00）专家怎么摆进机架：all-to-all、NVLink 拓扑与线缆物理学

**本章问题**：MoE 层在硬件上怎么布局？为什么"一个机架"是基本单位？

**讲透**：先画 MoE 层解剖图：token 进来 → 路由器（画成一个，实际每卡一份复制品，64 卡=64 份）决定送往少数专家（比如 1/32）→ 每个专家就是一个普通 MLP（升维投影→非线性→降维投影）→ 结果汇总相加 → 加上残差（原 token 直通车道，防止信息在层层变换中丢失）。

标准布局是**专家并行（EP）**——Reiner 强调"这是标准做法，也是最优解"：不同专家放不同 GPU。DeepSeek 256 个专家 / 72 卡 Blackwell 机架（256÷72 不整除，干脆忽略 8 张卡，64 卡 × 每卡 4 专家；画图简化为每卡 2 专家）。通信模式是 **all-to-all**：任何一张卡都可能要把 token 发给任何其他卡（路由结果不可预测）。幸运的是 Nvidia 的机架设计——GPU 贴柜壁、NVLink 交换机居中、每卡线缆直连交换机、任意两卡**两跳**直达——和 all-to-all 是天作之合。

**但机架是硬边界**：跨机架走 scale-out 网络，带宽只有 scale-up 的 **1/8**。MoE 层跨两个机架 = 平均一半 token 要走慢 8 倍的网 → all-to-all 被卡死。所以**一个 scale-up 域能装下的专家数，就是一层 MoE 的上限**——这是"越做越大互联域"的根本动机。

Dwarkesh 问了个好问题：为什么不把机架做大/用更大的交换机把两个机架连起来？答案分两层：①单一大交换机方案存在，但布线拥塞（cabling congestion）让你必须用交换机层级；②更根本的是**线缆密度物理学**——GPU 数翻倍 = 垂直走线密度翻倍，还要考虑线缆弯曲半径（光缆不能折死，会断）、tray 到背板的接插件密度、机柜承重（加固→更重→再加固的死循环）、供电、散热。Dwarkesh 连呼意外："机架那么大，居然塞不进更多线缆？"Reiner：优化过的现代机架内部非常紧，所有物理约束都在推向极限。代际进步的真相：**Hopper(8 卡)→Blackwell(72 卡) 基本只是产品决策**（从托盘 tray 形态改成机架形态，无实质技术壁垒）；**Blackwell(72)→Rubin(500+) 有一点 Jensen math（营销口径），但至少有真实的 ~4 倍提升**，来自全新且困难得多的机架布线设计。

**连接主线**：互联域大小决定 MoE 上限 → 那模型规模史就对上了——下一章。

### 第 8 章（46:00–50:00）为什么 5 万亿参数模型直到现在才出现

**本章问题**：GPT-4（2023，传闻 >1T 参数）发布后三年，为什么参数量最近半年才显著突破？不是"三年没 scaling"吗？

**讲透**：因为**推理侧装不下**。Dwarkesh 提出假说："是不是就因为在等一个能装下 5T 参数+足够多用户 KV cache 的机架？" Reiner 确认：Hopper 时代 8 卡 scale-up 总共 **640 GB**（2022 年）——1T 参数 FP8 就要 1TB，加上 KV cache 根本没戏。Blackwell 机架 scale-up 到 **10-20 TB**，5T 参数 + 海量 KV cache 才放得下。**部署更大的 scale-up 域是重大解锁**（"a huge unlock"）。换个角度说：模型不是"训练不出来"，是"serve 不起"——训练一个大模型可以跨很多机架慢慢跑，但要低延迟服务用户，就得装进一个 scale-up 域。

顺带解释了 Gemini 之谜：Google（TPU）很久以前就有超大 scale-up 域，所以 Gemini 的预训练成功史比别家长——**领先可能不是算法，是基础设施**。当然 Reiner 声明自己当时不在场，无法拆分多少来自更大稀疏度、多少来自 MoE 细节、多少来自训练数据——但"**激活参数受算力成本限制，总参数受 scale-up 域大小限制**"这条硬约束是确定的。

**连接主线**：装得下之后，训练和推理怎么把多机架组织起来？——并行策略登场。

### 第 9 章（50:00–58:30）四种并行怎么选：切法贴着模型架构走

**本章问题**：专家并行、流水线、张量、数据四种并行，实战怎么组合？

**讲透**：全片最美的结论之一：**最好的并行策略物理上长得就像模型架构本身**——不是 galaxy brain 花活。Dwarkesh 原话："最有意思的是，实战中最好的并行策略，物理上长得就像模型架构本身。不是什么天才设计——有专家，就把专家放不同 GPU；有层，就把层放不同机架。切割方式贴合模型架构。" Reiner 补了"galaxy brain 视角"：模型有很多可切的维度——层数、模型维度、DFF 维度、专家数——理论上每个维度都能切，但只有"够大"的维度切了才划算，实战选中的就是专家和层两个。

- **EP（机架内）**：all-to-all 强烈要求全连通 → 天生属于单个 scale-up 域；
- **PP（跨机架）**：把模型**层**切到不同机架。通信量分析（本章核心推导）：机架内每层 all-to-all 要发"激活专家数 × 每段层数 × 2（进出各一次）"份数据，而跨机架只发 1 份原始 token。要求 (1/8 带宽差) × 激活专家数 × 每段层数 × 2 ≥ 1，激活专家数通常 ≥8（光这一项就够 8），轻松满足 → **一个机架当一段流水线完全可行**，可以串很多段。
- **TP（张量并行）**：切单个矩阵。现在专家本身太小，切了不值得——**已被时代淘汰**（对推理；"专家变小后 relevance 大幅下降"）。
- **DP**：复制模型喂不同数据，多机架训练的天然外层。

Dwarkesh 补充两段权威告诫：①Ilya 说过"今天我们知道别用流水线并行"（训练语境）；②Horace He（前 PyTorch 核心、现 OpenAI）给他们小圈子讲课时说：**PP 除了气泡（下章）还会约束架构设计**——比如 Kimi 的残差要跨层回看几层前的 attention，流水线切开后实现很痛苦。但 Reiner 用后面的推导为 PP 平反：它有真实好处（第 11 章），值得这些麻烦。

**连接主线**：PP 的代价是气泡和微批——下一章画图。

### 第 10 章（58:30–67:00）流水线气泡：训练和推理为什么完全不一样

**本章问题**：什么是气泡？为什么推理里不成问题、训练里是老大难？

**讲透**：画时间×机架的甘特图（横轴时间，纵轴四个机架）。推理：4 个机架 = 4 道工序，请求 0 走完 R1 就可以立刻让请求 1 进 R1……把时间表填满，**推理里根本没有气泡**——你随便往里塞请求就行。Reiner："在推理语境下这改动太自然了，谁会干等啊？"原因：decode 本来就是循环（生成 token→写 KV→再前向），微批和批没有本质区别——Dwarkesh 恍然大悟："微批 vs 全批的区别在推理里根本无所谓，因为你爱怎么叫都行。它只在训练里才要紧，因为训练存在最优 batch size。"

训练完全不同：**反向传播必须对"一整个批"同时做**（Dwarkesh 追问出的关键澄清）。于是时间表是：前向跑 N 个微批 → **硬停** → 所有人一起反向。为什么硬停凑整批？因为存在最优 batch size，而且是两股力量的对撞：**ML 收敛角度批越小越好**（梯度最新鲜——"你永远在用最新的信息做梯度下降"）；**系统角度批越小越亏**（算力利用率崩）。最优是两者的权衡，所以批不能拆散迁就流水线 → 硬停 → 气泡出现。文献里的缓解方案：1F1B（one-forward-one-backward，一前一后交错）、zero-bubble（精细排期填洞）。Reiner 笑评：**"气泡里可以挖比特币"**——更正经的用法是提前算权重梯度那一步。

另插一段 Jane Street 的 Axel（GPU 性能工程师，Dwarkesh 赛前功课）的观点作引：**pipelining 强制你用 micro-batch 而非全批 → 定义上就无法把权重加载摊到所有序列上**。代价是不能摊权重读取，收益是每卡要装的显存变少——第 11 章正式算这笔账。

**连接主线**：气泡是 PP 的代价，那 PP 的收益到底是什么？下一章算内存账。

### 第 11 章（67:00–75:00）显存容量账：内存墙悖论、pipelining 省权重不省 KV

**本章问题**：既然说 Blackwell 机架内存"过剩"，PP 到底图什么？——以及一个当前行业最热的悖论。

**先讲悖论（本章引子，v2 补）**：Dwarkesh 抛出当下的行业热议：**内存墙**——内存贵上天、产能不够，Dylan Patel（SemiAnalysis）说 **hyperscaler 今年 ~50% 的 CapEx 花在内存上**（hyperscaler CapEx 是高千亿到万亿美元级——这是一笔骇人的约束），**手机出货量预测因此砍 30%**（内存被 AI 抢走了）；但黑板推导刚说完机架显存"过剩"（1T 参数只要 1TB，机架有 10-20TB）——**"Jensen 为什么往机架里塞这么多用不掉的显存？！"** 这个悖论的解答正是本章的内容：过剩的只是"装权重"那一半需求；真正吃显存的是 KV cache（batch × 上下文 × 每 token 字节），它才是把全球内存产能吸干的需求方。权重放得下 ≠ 显存够用。

**正式算账**：显存需求 = 总参数 + batch × 上下文长 × 每 token 字节。除以 E（专家并行的卡数）× P（流水线段数）得到每卡需求。P 越大，权重一项摊得越薄——**PP 完美解决权重的容量问题**。

但 KV 一项 P 会抵消：填满 P 段流水线需要 **P 个微批同时在飞**（微批数 = 流水线段数，"proof by visual"——甘特图上数格子就是 4×4），每段机架要同时容纳 P 份微批的 KV → 分子分母的 P 约掉了。**KV cache 既不能跨用户摊（每用户独有），也不能跨流水线段摊（每段都要伺候在飞的微批）——两头都省不掉**（Dwarkesh 中途猜错一次——"每段只存自己那几层的 KV 不就省了？"Reiner 引导他自己发现"在飞序列数变多了"，两个效应正好抵消）。推论：**"先证明 KV 不能跨 batch 摊，现在又证明它不能跨流水线段摊——它从两头看都很惨。"**

实战结论（DeepSeek 论文背书，他们公开汇报了做法）：**EP 拉满到 scale-up 域大小（64），PP 少用或不用（最多 2 段意思一下，让权重存储别太夸张）**。PP 真正的价值场景：模型大到超出一个机架（极稀疏模型）。另一个隐藏含义（MatX 的生意逻辑）：既然单机架装得下权重，理论上可以造"每卡显存更少"的更便宜硬件。

**跨机架的延迟代价（v2 补具体数字）**：每一跳 rack-to-rack 的路径是 GPU→网卡→（可能经数据中心交换机）→对方机架网卡→GPU，延迟**每跳几毫秒量级**（Reiner 坦言"我没把握，可能差一个数量级"），而且 decode 是串行的——**每一层、每个 token 都要逐段跳，延迟跨阶段叠加**。4 段流水线 ≈ +10ms/token，把 20ms 的 baseline 拉到 30ms——Dwarkesh："10ms/token 其实很多了。" 这是实战少用 PP 的第二个原因。

**scale-up 域真正值钱的是带宽，不是容量（v2 补关键推导）**：权重读取时间 = N_total ÷ (GPU 数 × 每卡带宽)。每卡带宽每代只涨 1.5~2×，但 scale-up 域从 8 卡→72 卡 = **聚合带宽直接 ×9**——所以大 scale-up 域把 t_memory 延迟大幅打下来（"massively improved"）。Reiner 金句：**"Pipelining 完全解决容量问题，但 scale-up 大小解决的是带宽问题；而带宽问题让你能做更长上下文——模型越 agentic 这越重要。"** 反例：把极稀疏模型塞进一台小 H100 盒子，延迟会非常高。这也再次呼应第 8 章：Google 早年大 scale-up 域的优势，一半在容量（装大模型），一半在带宽（低延迟 serve 长上下文）。

**连接主线**：服务侧（内存/带宽）讲完了，转训练侧的算力分配——economics 登场。

### 第 12 章（75:00–88:00）训练算力怎么分：6ND、RL 的低效率与"100 倍过度训练"

**本章问题**：Chinchilla 说训练算力最优时每参数 20 token。但训练出的模型还要服务用户——联合最优是什么？

**讲透**：Reiner 的启发式：**总成本 = 成本A + 成本B，A 随一边递减、B 随另一边递增时，最小值大致在 A=B 处**（1/x 对 x、e^x 对 e^-x 都成立；幂律族普遍如此——"遵循幂律的东西往往有这个性质"）。应用到三项成本：

- 预训练：**6ND**（前向 2 + 反向 4，"6ND 公式"）
- RL：同样是 N × token 数，但两个低效叠加：只训练部分 rollout（~30%），decode 的 MFU 天生比训练低 → 每 token 有效成本是预训练的 2~6 倍（"如果对每条生成都做反向就是 6ND，但很多生成不训练，所以下限是 2，取 2~6 之间"），折算系数 α≈2/10
- 推理：纯前向 = **2ND** → 每 token 成本是预训练的 1/3，再乘 decode 低 MFU 的 30%，β≈1/10

三项成本相等 → 令预算各占 1/3（Reiner 强调 33/33/33 只是 ballpark，25/50 也大差不差——"33 和 25 差别不大"）。代数化简后**激活参数项全部约掉**，剩下漂亮的近似：**推理 token 总量 ≈ 预训练 token 总量 ≈ RL token 总量（同数量级）**。

这场推导还有个花絮值得记：Reiner 白板上当场算错一次（α 写成 1/10 导致"RL 永远不做反向"的荒谬结论），Dwarkesh 抓住才改回 2/10；改完 Reiner 自嘲了一句很有味道的话——**"这个系数是 1.5，那个是 1，数十亿美元的算力就往反方向流了。如果你用电子表格认真建模，也许就能发现钱正在流进下水道。"**（对做交易的人应该很有共鸣：模型系数差一点，仓位方向就反了。）

代入真实数字验证（他在白板边算边让 Dwarkesh 拿计算机验算，我也复算 ✓）：全球推理流量 ~5 亿 token/s × 2 个月生命周期 = 2.6×10^15；除以 10（模型家族多个型号分摊）→ 单模型 ~50M token/s × 2 个月 ≈ **260 万亿** token；传闻 GPT-5 预训练 ~150 万亿 token——同数量级，吻合！再用 100B 激活参数算 Chinchilla 最优 = 20×100B = **2 万亿** token → 实际 150-200 万亿 ÷ 2 万亿 = **过度训练约 100 倍**。

**"人们会往哪边错？"（v2 补）**：Dwarkesh 追问：预测不完美时，这个平衡会偏向哪边？Reiner：**要给推理项按概率打折（derate）**——你训练的模型有一定概率不是 frontier、被整个扔掉，那部分训练投入对应的"未来推理收益"就归零；所以理性做法是把推理 token 期望值调低 → **实际上会往训练侧多投一点**（over-train 得更狠）。

这给出 Dwarkesh 惊叹的金句：**"每个用户从 GPT-5 拿走的输出 token 总量，应该约等于喂给它的预训练 token 总量——每个模型都应该在输出端'再生一遍全人类知识'"**。以及方法论金句："这就是为什么要到处做近似——误差棒很大，但把 A=B 一摆，就能从第一性原理推出这些数字，太爽了。"

**连接主线**：成本公式不仅决定训练，还反向被定价表泄漏——下一章当侦探。

### 第 13 章（88:00–107:00）从 API 定价反推模型机密（全片最好玩的侦探戏）

**本章问题**：公开定价表里藏着模型的哪些秘密？

**讲透**：Reiner 的观察起点：**"你被激励定价贴近成本——否则别人会抢你生意"**——所以定价 ≈ 成本的直接投影。三条线索逐一破案：

**线索 1 — Gemini 3.1 超 200K 上下文贵 50%**。把成本画成上下文长度的函数：算力成本平的（与上下文无关），显存成本 = 权重常数 + 随上下文线性涨的 KV 项，max 后有个拐点。**定价拐点 ≈ 成本拐点**（"这个 bump 在 200K，说明它大体对齐了 crossover 点"）。令拐点 = 200K，权重项已被大 batch 摊薄忽略，解出**每 token KV 字节 ≈ 激活参数/(300×200K) = 100B/6000万 ≈ 1667 字节 ≈ 2KB**（我复算 ✓）。这个数合理吗？KV 字节 = 层数 × 2 × 每头维度 × KV 头数。**Character AI 的招数**（博客公开，Gemma 模型也用了）：全局上下文跨层共享 → "层数"=1；8 个 KV 头 × d_head=128 × 2（K和V）= **2048 字节**，正好对上！或者稀疏注意力路线：各项调大再除以稀疏度。**一个定价数字，反推出 Gemini 大概率用跨层共享 KV 的类 Character AI 架构**。Dwarkesh："他们通过 API 定价泄漏了这么多架构信息，太逗了。"（Q 头/KV 头的区别见名词表——存储的是 KV 头，检索的 Q 头用完就扔，所以只有 KV 头进这个公式。）

**线索 2 — 输出 token 比输入贵 5 倍**。先看真实对话的时间线（v2 补）：一段聊天其实是 **decode↔prefill 交错**的——用户发消息（短 prefill）→ AI 逐字回复（decode）→ 工具调用/读文件（长 prefill）→ AI 再回复（decode）……然后把"一趟前向处理的 token 数"（len_pass）做横轴：decode=1（一次只算 1 个新 token，但整套权重+KV 要读一遍），prefill=几百上千（一趟算几百个 token，读的还是那一份显存——flash attention 下 prefill 的中间结果根本不落显存）。除以 len_pass 后：算力的单 token 成本是平的；显存的单 token 成本随 len_pass **下降**（同一份显存读取摊给更多 token）。输出贵 5 倍 = **decode 时显存时间 ≈ 算力时间的 5 倍 = 推理被显存带宽死死卡住**（"it is, in fact, tremendously memory bandwidth bottlenecked"）。这就直接回答了开篇 Fast Mode 之谜：低延迟=小 batch=显存带宽利用率低=贵，你付的 6 倍钱买的是"不拼车"。而 prefill 是 compute-bound，所以输入便宜。

**线索 3 — 缓存命中便宜 10 倍，写入收 1.25 倍钱**。KV cache 有两种生产方式：从头算（remat，重跑前向，按算力计价）或之前算好存着。存哪层？四层存储（HBM/DDR/Flash/机械硬盘）各有两个价格：**持有成本**（占用容量的比例 × 该层每秒租金）和**取出成本**（搬回 HBM 的带宽时间）。选择的经济学（Reiner 给的判据）：**持有时间 ≈ 该层 drain time × 容量占用比例**——直觉版：你要存一个东西的时长，应该约等于"把这个层级完全腾空/装满一遍"的时间乘上你占了它多大比例，两边成本刚好打平。各层 drain time（我复算 ✓）：HBM 20ms → DDR 秒级（1-10s）→ Flash ~1 分钟 → 机械硬盘 ~1 小时。对照 OpenAI 的两档定价——**5 分钟档** ($5 基础价，写入 $6.25/M) 和 **1 小时档**——5min≈300s 对上 Flash 量级，1h=3600s 对上 HDD 量级，**两档刚好对应 Flash 和机械硬盘**！Dwarkesh 震惊 double：①2026 年了，LLM 推理的缓存居然存在**机械硬盘**上；②它慢到读完全容量要一小时——"这技术真不讨喜，但总有用得上的地方"（Reiner）。

**连接主线**：显存带宽墙不仅决定价格，还锁死了上下文长度的未来——下一章。

### 第 14 章（107:00–121:00）为什么上下文长度卡在 200K：显存带宽墙

**本章问题**：Dario 说过"AGI 不需要持续学习，上下文学习就够了"——那需要 1 亿 token 上下文（相当于一起工作一个月的员工）。为什么没人做出来？

**讲透**：先补一个"为什么没有二次项"的澄清（Dwarkesh 问：注意力的计算量随上下文二次涨，怎么你的公式里没有？）：有，但摊到**每 token** 后是线性的且**斜率极低**——权重矩阵乘法那条平线占绝对主导，二次项要到**百万 token 量级**才显形。所以长上下文的两个成本里，**算力成本几乎无罪**。

**真正的墙是显存带宽和容量**——每个新 token 都要把全部历史 KV 读一遍，200K×2KB=400MB/用户/前向。历史佐证：GPT-3 的 8K → GPT-4 时代 100-200K，然后**近两年全行业原地踏步**——Reiner 的解读：这个停滞本身就是证据，说明 200K 就是当前硬件下的成本平衡点，再往上是"成本 prohibitive"。稀疏注意力是唯一出口（把线性变 √L），但太稀疏质量就掉（"你只看极小一部分 token，质量必然变差"）；也可能现有模型的 200K 已经 priced in 了稀疏注意力。Reiner 直言："**我实际上看不到很好的解决路径。HBM 就在那里，没有大幅变好。**"——如果 Dario 的"上下文学习足够论"成立，那 ML infra 必须先出一次大变化才撑得起 1 亿 token。

**连接主线**：黑板部分收尾，最后是轻松的跨界彩蛋。

### 第 15 章（121:00–133:00）彩蛋：密码学与神经网络的殊途同归

**本章问题**：Reiner 博客里"密码协议架构长得像神经网络"是什么意思？

**讲透**：方向相反、机制同源：**密码学把有结构的信息打乱到看不出随机（雪崩效应：输入改一位，输出天翻地覆）；神经网络从看似随机的数据里提取结构**（蛋白质序列、DNA、乱码 → 高层结构）。一个佐证：**随机初始化的神经网络本身就是个不错的密码**（随机权重=乱搅一通），是**梯度下降把它驯化成可解释的**——ResNet 残差和 LayerNorm 都是在刻意"保护导数不让它过于复杂"。而密码学的头号攻击手段恰是"求导"：**差分密码分析**（differential cryptanalysis）——密码跑在 GF(2)（只有 0/1 的域）上，照样能差分：好密码的设计目标是"输入小改→输出天翻地覆"，而这在神经网络里正是**对抗样本**——同一性质，密码学求之不得，神经网络避之不及。两者的交汇点：**LLM 后门 = 往反向传播里藏一个输入**（不进前向，但进 backward）——对抗攻击/后门恰好展现出密码学的雪崩性质。Dwarkesh 问"用神经网络造密码成功吗？"——Reiner：反方向（密码→网络）很 productive，正方向（网络→密码）危险：**没经过十年锤炼的密码基本都被破了，99% 都活不下来**。

具体的 productive 案例：**Feistel 网络**——用一个不可逆的 f(x) 构造可逆的 (x, y)→(y+f(x), x)：x 直接透传可读出，y 用 z−f(x) 反解。密码学用了几十年的主流构造；2017 年 **RevNets** 论文把它搬进神经网络——x 过 transformer 层加到 y，原 x 变新 y，隔层形成大残差。**整个网络可逆后的妙用：训练时不用存激活值**——反向传播时倒着把前向重算出来（rematerialize），**用计算换显存**。和 KV cache 恰好是镜像策略：**KV cache 花显存省计算（"以当下硬件的行情，这通常划算"——Reiner），RevNets 花计算省显存**。

## 4. 核心思想清单（可直接引用）

 1. **"主导效应是 batch size。"** —— Fast Mode 谜题的答案第一句。
 2. **不拼车的成本可以比拼车差 1000 倍**——推理经济学的一切从此展开。
 3. **最优 batch ≈ 300 × 稀疏度，与模型大小无关**——硬件算力/带宽比值三代稳定在 ~300。
 4. **偏离甜点区直接掉 MFU**：最优拐点 100K 跑 200K，MFU 约减半——服务商都守在 Goldilocks 区。
 5. **"一台机架 ≈ Gemini 流量的千分之一"**——AI API 市场的入场券；推理规模经济的中心化推力比想象弱。
 6. **MoE 用 64 倍参数换 4 倍等效——在 batch 摊薄权重的世界里是纯赚，做到"用户不够凑批为止"。**
 7. **激活参数受算力成本限制，总参数受 scale-up 域大小限制。**
 8. **最好的并行策略物理上长得像模型架构**：专家→GPU（EP），层→机架（PP）；张量并行已被"专家变小"淘汰。
 9. **KV cache 两头省不掉：不能跨用户摊，也不能跨流水线段摊。**
10. **pipelining 解决容量问题，scale-up 大小解决带宽问题**；带宽才让你敢做长上下文——agentic 时代的关键。
11. **"每个模型都该在输出端再生一遍全人类知识"**——推理 token 总量 ≈ 预训练 token 总量；预测不完美时还要给推理项打折，实际上更偏训练侧。
12. **前沿模型过度训练约 100 倍（Chinchilla 口径）**——训练多花钱是为了推理单 token 便宜。
13. **"系数 1.5 vs 1，数十亿美元算力就往反方向流"**——电子表格建模的意义。
14. **API 定价是架构机密的泄漏**：200K 拐点 → 跨层共享 KV（≈2KB/token）；输出 5× 价 → decode 带宽瓶颈 5:1；缓存 10× 便宜 → Flash/机械硬盘分层。
15. **上下文卡在 200K 不是算力问题，是显存带宽墙；"我看不到很好的解决路径。"**
16. **花显存省计算（KV cache）通常划算；花计算省显存（RevNets）是镜像操作**——以当下硬件行情，前者占优。
